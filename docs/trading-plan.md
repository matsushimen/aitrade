# 開発ロードマップと取引条件

## 1. 取引条件

`config/baseline.json` を正とする。BTC/JPY現物・買いのみ・5分足・JST日次区切り。
元手10,000円、エントリー費用込み保有上限5,000円、1取引のモデル上の損失予算100円、
日次実現損益が−200円以下なら新規取引を停止する。買い直しは翌JST日から。
損切り基準はエントリー参照価格の2%下。損切りに両側コストを含めて数量を小さくする。
日次損益は利益と損失の通算であり、損失額だけの累計ではない。
価格ギャップや通信停止を含む実損失の上限保証ではない。

SMA12がSMA36を上抜けた確定足の次足以降に買い、下抜けで売る。
23:55 JST以降は新規買いをせず手仕舞う。現物ポジションは同時に1つ。
数量は小数点以下8桁で切り捨てるが、これは取引所の最小数量確認を意味しない。

費用は片道手数料15bps、片道スリッページ5bpsという**研究用の仮定**。
`spread_bps` は往復スプレッドで、履歴検証では片側に半分ずつ加える。
既定0bpsは従来どおりスリッページにスプレッド相当を含む仮定であり、ゼロスプレッドの確認値ではない。
スプレッドを別に設定する場合は、スリッページとの二重計上に注意する。
実時間paperは実際に観測したaskで買い、bidで売り、さらに仮定の手数料とスリッページを加える。
そのため実時間paperで設定上のspreadを再度加算しない。

## 2. データ

bitbankのUTC日付パーティションを取得し、JSTの対象範囲だけSQLiteに保存する。
生JSONはAPIのUTC日付名。現JST日がUTC日付より先でも未来のAPIパーティションは要求しない。
確定済み足のみ保存し、時刻ずれ・欠損・異常OHLCV・重複を検出するとDB更新を止める。
CSV出力も288本/日の連続性を検査し、不正データでは既存CSVを置き換えない。
既存形式とCLIを維持し、過去の欠損は該当JST日を再取得して修復できる。

## 3. 基準戦略と未使用期間評価

`evaluate.py` は開発期間と後続の評価期間の重複を拒否し、同じ設定・費用で実行する。
両期間はそれぞれ元手とSMAウォームアップをリセットする。設定とCSVのSHA256を結果に記録する。
このコマンドはチューニングを行わない。過去に見た期間かどうかは人が管理する必要がある。
評価結果を見てルールを変更したら、その評価期間を未使用期間として再利用しない。
今回、ルールを変更せず、2026-10-20〜22を開発用、10-23〜25を未使用の評価用に事前固定した。
短期間の機能検証であり、戦略の有効性を確定するものではない。

## 4. OpenAI API互換LLM補助

`llm_assist.py` は確定足36本だけを指定したOpenAI API互換のChat Completionsエンドポイントへ送る。ニュース収集は未実装。
接続先は`--base-url`または`OPENAI_BASE_URL`で設定する（バージョンパスを含める）。
既存CLIとの互換性のため未指定時は`https://api.openai.com/v1`を使う。
APIキーは`--api-key-env`で指定する環境変数（既定`OPENAI_API_KEY`）、モデルは`--model`で明示する。
認証不要のローカル接続は`--no-auth`でAuthorizationを省略できる。
`--response-format`で`json_schema`（既定）・`json_object`・`text`を明示し、対応していない形式には自動フォールバックしない。
どの形式でもローカル検証で`regime`と500文字以内の`summary`だけを受け付ける。
`regime`は`risk_on`/`neutral`/`risk_off`。LLMは新しい注文や数量を決められず、
`risk_off`なら基準戦略の買いを見送る。欠損・期限切れ時も買いを見送る。売り・停止を妨げない。

記録には入力足の時刻、実際の応答受信時刻、モデル、プロンプトのSHA256を含む。
入力足の確定前や応答受信前の取引には使えず、入力確定から60分を過ぎた分類は失効する。
過去データを今分類しても受信時刻を過去に戻さないため、その過去期間の取引には利用できない。
歴史的知識を持つLLMの後付け分類では独立評価にならない。今後の期間で分類を先に蓄積し、
その後に同じ期間のbaselineと比較する。API呼び出しの料金は売買コストとは別で、損益に未算入。

接続先・モデル・必要な認証の設定が未確定のため実モデル呼び出し・効果検証は未実施。
APIリクエスト形式、応答検証、時刻制約はモックで検証済み。

## 5. ペーパートレード

- `paper_trade.py`: 完了足の遅延シミュレーション。履歴の段階投入・再起動後も同じ結果を再現する。
  その足が確定してから次足始値約定を事後計算するため、実時間の注文執行検証として扱わない。
- `paper_quotes.py`: 公開tickerの観測ask/bidで市場注文の仮想約定を記録する。
  初回のSMAウォームアップは過去足で行うが、過去の仮想注文を生成しない。
  新しい確定足から90秒以内の上抜けだけを買い判断に使う。取り逃した足の買いを後から実行しない。
  同じquoteやシグナルの再処理で二重約定しない。時刻、判断理由、数量、費用込みキャッシュフローを記録する。

状態はファイルロックと一時ファイルの置換で保存。設定変更は新しい状態ファイルを要求する。
データ欠損、古いquote、異常値、既処理データの変更は新規処理を停止し、既存状態を維持する。
`--halt`は永続的に新規買いを禁止する。quote方式は次に取得できた新鮮なbidで売る。
履歴方式は次の未処理足で売る。通信断中の即時手仕舞いはできず、ポジションは保存状態に残る。
停止後に再開する場合は別のpaper状態を作る。LLMモードの途中切り替えも別状態とする。

quote方式は観測した入力足・quote・受信時刻・LLM判断を保存し、`--replay`で完全再現を確認できる。
履歴方式と一致すること、および実quote方式との差が説明できることを別々に検証する。
差の要因は、始値と観測ask/bidの違い、実スプレッド、ポーリング遅延、取り逃し、
足内low到達と観測bid到達の違い。板厚・部分約定・取引所の注文受付は両方式とも未モデル化。
長期運用では状態ログが増大するため、ローテーションと監視を追加する必要がある。

## 6. 小額の実運用への進行条件

今回の実装には取引所認証、実注文、資金移動を含めていない。
ロードマップの依頼は受けているが、先行段階の完了条件はまだ満たしていない。
未使用期間でbaselineは損失、LLM比較は未実施、実時間paperの継続運転は未確認。

次の開発では、実モデルの判断を蓄積した未使用期間での比較と、実時間paperの連続運転・障害試験を先に行う。
その後、現行の取引所手数料、最小注文数量、数量/価格刻み、注文状態と残高の照合、
部分約定、タイムアウト時の照会、再起動時の注文復元を実装・検証する。
実注文の上限額、累計損失停止額、日次停止額、停止後の保有ポジションの扱いは専用設定に固定する。
研究用の5,000円/100円/200円を、そのまま確認済みの実運用条件として流用しない。
実注文を開始する前に、これらの具体的条件と検証結果を提示する。
